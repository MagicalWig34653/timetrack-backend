## Befunde

1. **`*_FILE` wird vom Backend nicht unterstützt** (`Configuration.swift`, `StorageService.swift:24`, `NotificationRuntime.swift:44` lesen nur Umgebungsvariablen). Gelöst im Image durch `scripts/docker-entrypoint.sh` (fünf Variablen, Exit 64 bei beidem gesetzt, 66 bei unlesbarer Datei). Wer das Backend außerhalb des Images mit `*_FILE` startet, bekommt keine Wirkung. Alternative im Swift-Code (nicht umgesetzt): Hilfsfunktion in `Configuration` und `StorageEnvironment`.
2. **Client-IP hinter Proxy**: Rate-Limits (`AuthRateLimitMiddleware`, OAuth, OIDC) nutzen `req.remoteAddress` und ignorieren Forwarded-Header bewusst; es gibt keine Trusted-Proxy-Konfiguration. Hinter einem Proxy teilen alle Clients einen IP-Zähler (60 je 5 min): Anmeldesperre für alle durch einen Angreifer möglich. Abhilfe am Proxy, kleinste Codeänderung (`TRUSTED_PROXY_CIDRS`) in BETRIEB.md Abschnitt 6.
3. Lokale Dateien sind an den echten Pfad gebunden (`storage_location`); Restore auf anderen Pfad macht sie unlesbar, bis SQL umschreibt. Skript warnt.
4. Das Image enthält keine `sqlite3`-CLI und keinen MariaDB-Client; Backup läuft auf dem Host bzw. mit `--db-container`. SQLite in einem benannten Docker-Volume: Hilfscontainer nötig, nicht ausgeführt.
5. `/ready` wird als Container-Healthcheck der Stack-Vorlage benutzt (bewusst: ohne Migration nie healthy, Rollout rollt zurück); bei DB-Ausfall werden Tasks ebenfalls ungesund. Kein `/metrics`.
6. Migration → Backend-Wechsel im Update hat ein Zeitfenster altes Backend ↔ neues Schema; nur bei additiven Migrationen sicher, nicht geprüft.
