# L1 – Linux-Testfehler in CI

Stand 17.10.2026, Branch `l1-linux-tests`. Nicht gepusht, nicht gemergt.

## Ursachen und Korrekturen

1. `testC19StorageSQLite` (`duplicate column name: storage_location`): kein Migrationsfehler. Der Test führt `BindStorageLocations.revert` und `.prepare` über `app.db` aus; `:memory:`-SQLite hat einen Pool mit einer Verbindung je Event Loop. Auf Rechnern mit wenigen Kernen (CI: 2) landen die beiden Aufrufe auf verschiedenen Verbindungen, die das DDL der jeweils anderen nicht konsistent sehen (danach auch `no such column`). Reproduziert nur mit `--cpuset-cpus 0,1`, nicht mit vielen Kernen (macOS, Docker ohne Begrenzung). Fix: beide Schritte in `app.db.withConnection { }` auf einer Verbindung. Produktivcode unverändert (Migrationen laufen einmal beim Start).
2. `testContractResponseShapes` und 3. `testJSONSerializationRoundTripBooleans`: swift-corelibs-foundation liefert aus `JSONSerialization` kein unterscheidbares Bool-`NSNumber` (`true` wurde als Zahl 1 gelesen). Fix: `JSONSchemaValidator.parse(_:)` dekodiert per `JSONDecoder` in einen internen Wert-Enum und liefert native Swift-Typen (`Bool`, `Int`, `Double`, ...); Bool-/Zahlenerkennung arbeitet auf diesen Typen (unter Darwin weiterhin zusätzlich `CFBoolean`). Verträge und Antworten werden damit geparst (`ContractSupport`, `ContractShapeTests`).
4. MariaDB-Variante: nichts MariaDB-spezifisch Linux-Fehlerhaftes gefunden; alle Tests grün (siehe unten).

## Läufe (alle lokal ausgeführt)

- Linux arm64 (swift:6.3-noble), SQLite, 2 CPUs: 305 ausgeführt, 35 übersprungen, 0 Fehler.
- Linux arm64, MariaDB 12.3.3 (Dev-Container, eigene DB `timetrack_test_l1`, danach gelöscht): 305 ausgeführt, 1 übersprungen (Auth-Lock-Benchmark), 0 Fehler.
- macOS: 305 ausgeführt, 35 übersprungen, 0 Fehler.
- Nicht geprüft: echter amd64-Lauf (Swift-Compiler stürzt unter Rosetta ab); der Kernzahl-Effekt wurde stattdessen über `--cpuset-cpus` nachgestellt.
