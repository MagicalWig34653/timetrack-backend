## Routen
- `GET /.well-known/oauth-protected-resource` (+ `/mcp`-Pfadvariante nach RFC 9728), `GET /.well-known/oauth-authorization-server`: Issuer = `PUBLIC_BASE_URL` (ohne Schlusszeichen `/`), Resource = `<Issuer>/mcp`. `OPTIONS` (CORS-Preflight, `*`) für Metadaten, register, token, revoke.
- `POST /oauth/register` (JSON, 201): nur öffentliche Clients, 1–5 Redirect-URIs (https oder http auf localhost/127.0.0.1/[::1], kein Fragment/Wildcard/Credentials/Leerraum, ≤ 2048), Name bereinigt (Steuerzeichen, `<>` entfernt, Leerraum zusammengefasst, ≤ 100 sonst Fehler; leer → Host), Fehler `invalid_redirect_uri` / `invalid_client_metadata`. Rate-Limit 20 / 5 min pro Peer-IP (eigener Zähler `oauth_register:`); ungenutzte Registrierungen (30 Tage, weder Request noch Grant) werden bei neuen Registrierungen gelöscht.
- `GET /oauth/authorize`: unbekannter Client / abweichende Redirect-URI → 400 JSON ohne Redirect. Danach Fehler als Redirect (`error`, `error_description`, `state`, `iss`): `unsupported_response_type`, `invalid_request` (PKCE S256 Pflicht, Challenge exakt 43 Zeichen base64url, State ≤ 512), `invalid_target` (`resource` ≠ `<Issuer>/mcp`), `invalid_scope`. Ohne `scope` werden alle 7 angefragt (im Consent abwählbar). Erfolg: 302 auf `<Issuer>/oauth/consent?request=<id>` (`no-store`, `Referrer-Policy: no-referrer`). Rate-Limit 30 / 5 min pro Peer.
- `GET /api/v1/oauth/requests/{id}`: Sitzung nötig (401), Request wird beim ersten Zugriff atomar an Konto und Sitzung gebunden; alles andere (fremdes Konto, andere Sitzung desselben Kontos, abgelaufen, entschieden, unbekannt) → 404. Recovery-Sitzungen 403.
- `POST /api/v1/oauth/requests/{id}/decision` (CSRF): `{approve, scopes?}`. Scopes müssen nichtleere Teilmenge der angefragten sein (sonst 400, Request bleibt offen). Einmalig (zweite Entscheidung 409). Deny → `redirectUrl` mit `error=access_denied` + `state`. Approve → Grant erzeugen oder aktiven Grant desselben Kontos+Clients wiederverwenden (Scopes ersetzt) + Code; `redirectUrl` mit `code`, `state`, `iss`. Alles in einer Transaktion.
- `POST /oauth/token` (form): `authorization_code` (client_id, redirect_uri, code_verifier Pflicht; optional `resource`) und `refresh_token` (optional engerer `scope`). Antwort: `access_token` (`tto_`+43 Zeichen, 1 h), `refresh_token` (`ttr_`+43, 30 d), `token_type: Bearer`, `expires_in: 3600`, `scope`; Header `Cache-Control: no-store`, `Pragma: no-cache`. Fehler RFC 6749: `invalid_request`, `invalid_client`, `invalid_grant`, `invalid_scope`, `invalid_target`, `unsupported_grant_type` (HTTP 400, JSON).
- `POST /oauth/revoke` (RFC 7009): immer 200. Refresh-Token → ganzer Grant; Access-Token → nur dieses Token; unbekannt/fremder Client → ohne Wirkung.
- `GET /api/v1/me/oauth-grants`, `DELETE /api/v1/me/oauth-grants/{id}` (204, widerruft Grant + alle Tokens sofort; fremd/unbekannt 404).
- `GET/POST /api/v1/me/api-tokens`, `DELETE …/{id}`: Anlegen verlangt frische Sitzung (403 `reauth_required`), Name 1–80, Scopes nichtleer ⊆ 7 Scopes, `expiresInDays` 1–365, Präfix `ttp_`, Klartext nur in der 201-Antwort; max. 25 aktive Tokens (409 `too_many_tokens`). Liste zeigt nicht widerrufene Tokens ohne Klartext.

## Öffentliche Schnittstelle für C17 (`BearerPrincipal.swift`)
`McpPrincipal { accountId, scopes: Set<String>, credentialKind: .oauthAccess|.personal, credentialId }` und `authenticateMcpBearer(_:on:now:) async throws -> McpPrincipal?`. nil bei: falscher Länge/Präfix, unbekannt, abgelaufen, widerrufen, Grant widerrufen, Konto deaktiviert, Refresh-Token (`ttr_`) oder Sitzungstoken. `credentialId` = Grant-ID (OAuth) bzw. API-Token-ID. Scopes = Token-Scopes ∩ Grant-Scopes ∩ bekannte (Verengen eines Grants wirkt sofort). `last_used_at` wird höchstens alle 60 s geschrieben (Grant bzw. API-Token). Der Aufrufer prüft Scope je Tool selbst.

Hinweis für C17/Lead: `DeviceScopeGuard` (AutomationService.swift) weist **jeden** Request mit `Authorization: Bearer` außer `/api/v1/automation/events` mit 401 ab. Für `/mcp` muss die Ausnahme dort ergänzt werden (außerhalb der C16-Dateirechte, daher nicht geändert). Ebenso ist `GET /mcp` ohne Ausnahme im `PWAStaticMiddleware` ein SPA-Fallback (405 laut ADR nur, wenn `/mcp` dort ausgenommen wird).

## Sicherheitsentscheidungen
- Codes: 32 Byte Zufall, 60 s, einmalig per bedingtem UPDATE (Affected-Rows, SQLite+MariaDB). Verbrauch vor Prüfung von PKCE/Redirect/Client/Resource: jeder Fehlversuch verbrennt den Code. Wiederverwendung oder verlorenes Rennen (parallel) widerruft den Grant samt aller Tokens (RFC 6749 4.1.2); bei paralleler Einlösung gewinnt genau ein Aufruf, der Grant wird danach widerrufen (Test).
- Refresh-Rotation: alter Refresh-Token wird atomar als verwendet markiert (`used_at`), neuer trägt `parent_id`. Erneute Vorlage eines rotierten Tokens widerruft den ganzen Grant. Abgelaufene/widerrufene Tokens → `invalid_grant` ohne Grant-Widerruf. Scope darf beim Refresh nur verengt werden. Alte Access-Tokens laufen regulär ab (1 h).
- Token/Revoke/Code-Prüfungen laufen unter der Auth-Serialisierung (`AuthService.transaction`); bei Fehlern wird das Ergebnis erst nach Commit als Fehler geworfen, damit Widerrufe bestehen bleiben.
- Request-Bindung an Sitzung: Hash des Sitzungstokens (`binding_hash`), erster Zugriff atomar; 404 statt 403, um Existenz nicht zu verraten.
- PKCE nur S256; Verifier 43–128 Zeichen aus dem RFC-7636-Alphabet. `resource` muss exakt `<Issuer>/mcp` sein (authorize und, falls angegeben, token).
- Redirect-URI-Abgleich exakt gegen registrierte Liste. Redirect-URLs enthalten nur `code`/`state`/`iss` bzw. `error*`; keine Tokens. Antworten der Token-Endpunkte `no-store`; Fehlertexte geben keine Eingabewerte zurück.
- Persönliche und OAuth-Tokens sind keine Sitzungen: `/api/v1/*` mit Bearer bleibt 401; Admin-Aktionen sind damit ausgeschlossen. Präfixe unterscheiden Typen (`tto_`/`ttr_`/`ttp_`), Länge fest 47.
- CORS `*` nur für Metadaten, register, token, revoke (öffentlich, ohne Cookies); nicht für authorize und `/api`.
- IP-Limits sind peer-basiert wie bei Login/OIDC (hinter Reverse Proxy zählt der Proxy). Das Token-Endpunkt hat bewusst kein IP-Limit (gemeinsame Ausgangs-IPs der Connector-Dienste; Geheimnisse haben 256 Bit Entropie).
- Es wird nichts geloggt (kein Logging von Bodies, Query oder Tokens im neuen Code; Vapors URL-Logging ist bereits durch die eigene Middleware-Kette ersetzt).
