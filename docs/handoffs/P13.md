# P13 – Planblöcke: Übergabe an PWA und Apple-Clients

Stand: 24.10.2026, Branch `worktree-agent-a34fccae7f0e10f5a`, API-Vertrag 0.29.0. Backend-Änderung im Worktree; Integration und Client-Anpassungen stehen aus. Maßgeblich: `contracts/openapi.yaml`, ADR-0028.

## Senden

`PUT /api/v1/plan/days/{date}` und die Einträge in `PUT /api/v1/plan/weeks/{isoWeek}` senden weiterhin `mode` (`office|home|customer|school|off`). Für einen geplanten Tag `blocks` als vollständige, chronologisch geordnete Liste senden. Jeder Block enthält:

```json
{
  "start": "08:00",
  "end": "12:00",
  "kind": "school",
  "placeId": null,
  "note": ""
}
```

`start` und `end` sind lokale Uhrzeiten `HH:mm` des Plantags (ohne UTC-Konvertierung); `end` muss später als `start` und spätestens `23:59` sein. Erlaubte Arten: `work`, `school`, `travel`, `office`, `home`, `customer`. `placeId` und `note` können weggelassen werden; die Notiz darf höchstens 200 Zeichen haben. Es gibt höchstens 32 Blöcke. Zwischen Blöcken darf eine Lücke liegen; gleiche Grenzzeit ist erlaubt, Überschneidung oder falsche Reihenfolge nicht. Bei `mode=off` nur `blocks: []` senden. Für einen Tag ohne Uhrzeiten ebenfalls `blocks: []`.

Ein vollständiges Beispiel für eine geteilte Schul-/Arbeitsschicht:

```json
{
  "mode": "office",
  "blocks": [
    { "start": "08:00", "end": "12:00", "kind": "school" },
    { "start": "13:00", "end": "17:00", "kind": "work" }
  ]
}
```

Jeder `PUT` ersetzt den gesamten Plantag, einschließlich der Blockliste. Die Woche bleibt atomar; `replace: true` löscht nicht genannte Plantage. Wenn `blocks` vorhanden ist, gewinnt es gegenüber `plannedStart`, `plannedEnd` und `plannedBreakMinutes`. Clients sollen deshalb beim Bearbeiten die gelesene Blockliste vollständig zurücksenden und die alten Zeitfelder nur anzeigen. Alte Clients dürfen weiterhin ausschließlich `plannedStart`, `plannedEnd`, `plannedBreakMinutes` senden; damit ersetzen sie eine detaillierte Blockaufteilung durch einen oder zwei einfache Blöcke.

## Lesen und Anzeigen

`GET /plan/days`, `PUT /plan/days`, `GET/PUT /plan/weeks` liefern am `PlanDay` stets `blocks` (auch leer) sowie die abgeleiteten Alt-Felder. Im Beispiel oben sind `plannedStart=08:00`, `plannedEnd=17:00`, `plannedBreakMinutes=60`, `plannedSeconds=28800`. `plannedSeconds` ist die Summe der Blockdauern und die Wochen-Plansumme addiert diese Werte nach den bisherigen Regeln für blockierte Tage. `planHints` enthält mögliche Hinweise `planned_break_short`, `planned_work_stretch_long`, `planned_break_part_short`; diese als deutsche, unverbindliche Planungshinweise darstellen. Die tatsächliche Pausen- und Rechtsbewertung bleibt getrennt.

`GET /time/weeks/{isoWeek}` ergänzt je Tag `planBlocks` (null ohne Plan), `planHints` und `planActualDifferenceSeconds` (= bewertete Ist-Arbeitszeit plus Gutschrift minus effektive Plandauer; null an künftigen und blockierten Tagen oder ohne Plandauer). Für Plan/Ist-Darstellungen jeden Block einzeln zeichnen, besonders bei Schule/Arbeit am selben Tag. Die bisherige `planMode` und `plannedSeconds` bleiben verfügbar. Auf einem durch Urlaub, Krankheit, Feiertag oder Freistellung blockierten Tag bleibt der gespeicherte Plan sichtbar, zählt aber effektiv als 0.

`GET /shares/incoming/{shareId}/view` und MCP `view_shared` liefern im Scope `plan` die Blöcke nur mit `start`, `end`, `kind`. Orte und Notizen der Eigentümerin oder des Eigentümers dürfen in Freigabeansichten nicht erscheinen. Der Kontoexport (`plan-days`) und MCP `list_plan_days` liefern die eigenen vollständigen Blöcke. MCP `set_plan_day` akzeptiert dieselben Schreibfelder wie REST.

## Fehler und Kompatibilität

HTTP 400: `plan_time_invalid` für ungültige Uhrzeit oder Ende vor/gleich Beginn; `plan_blocks_overlap` für Überschneidung oder falsche Reihenfolge; `plan_blocks_invalid` für mehr als 32 Blöcke oder Blöcke bei `mode=off`; `plan_kind_invalid` für eine unbekannte Art; `plan_note_invalid` für eine zu lange Blocknotiz. Ein fremder oder archivierter `placeId` bleibt 404. Der bestehende `plan_break_invalid` gilt für alte Schreibfelder. Client-Oberflächen zeigen dafür deutsche Texte; die Codes bleiben Englisch.

Vor API 0.29.0 kennen Server `blocks` nicht und würden sie ignorieren. Clients prüfen daher `apiVersion` aus `/api/v1/system/info`, bevor sie eine Blockbearbeitung aktivieren. Die PWA-Wochenplanung (P11) und Apple-Wochenplanung benötigen eine Client-Umsetzung; dieses Backend-Paket ändert keine Client-Repositories. Der Server liefert derzeit weder iCalendar-Feeds noch eine externe Kalenderbrücke. Eine spätere EventKit-Anbindung muss die Blöcke einzeln als Termine beziehungsweise Konfliktintervalle nutzen.

## Daten und Prüfung

Migration `p13.add_plan_blocks` ergänzt `plan_days.blocks`. Bestehende Zeitpläne ohne Pause werden ein Block; eine darstellbare alte Pause wird als Lücke zwischen zwei Blöcken erhalten. Extremwerte mit Pause mindestens so lang wie das Zeitfenster bleiben als Altwerte mit `plannedSeconds=0` erhalten, da kein positiver Block sie verlustfrei ausdrückt. Rücknahme löscht die Blockspalte; alte Felder bleiben. Keine Änderung an Ist-Abschnitten oder Kontorechten.

Prüfstand und offene Punkte werden nach dem vollständigen seriellen Testlauf hier und in `docs/STATUS.md` ergänzt.
