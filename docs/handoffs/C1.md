Stand: 14.10.2026, implementiert und lokal geprüft; externe Prüfungen unten offen. Ausführung: Codex; alleiniger Schreiber auf
`c1-db-foundation`, Worktree `timetrack-backend-wt/c1`. Keine Auth-Routen implementiert.
Erlaubte Änderungen: Package.swift, Sources/**, Tests/** und diese Übergabe.

## Implementierung

- SwiftPM-Bibliothek `TimetrackKit`, dünner Einstieg `App`, XCTest/XCTVapor-Testtarget.
- Konfiguration ohne Server instanziierbar: `Configuration(environment: [String: String])`.
- MariaDB-/SQLite-Konfiguration, SQL-Bind-Logging deaktiviert, Health/Readiness.
- Zehn öffentliche Fluent-Modelle und zehn benannte, rückwärts ausführbare Migrationen
  in `Sources/TimetrackKit/Migrations.swift`; Registrierung über `StageOneSchema.migrations`.
- `Sources/TimetrackKit/DatabaseSupport.swift`: atomarer Einmalverbrauch.
- Tests in `Tests/TimetrackKitTests/`: Konfiguration und gemeinsame DB-/HTTP-Tests.

## Schema und Verträge für C2

Alle Primärschlüssel UUID; Zeitfelder Foundation.Date/Fluent datetime, UTC als Instant.
Zeitfelder sind explizite Initializer-Parameter, keine impliziten Server-Zeitstempel.
Alle Fremdschlüssel verwenden RESTRICT; Widerruf/Deaktivierung statt implizitem Löschen.

| Modell / Tabelle | Wesentliche Regeln |
| --- | --- |
| Account / accounts | handle eindeutig, OpenAPI-Muster; role admin/member; optionale E-Mail und Verifikation |
| Passkey / passkeys | Account-FK; credential_id binär und eindeutig, 1–1024 Byte; Schlüssel binär; transports JSON; Zähler nicht negativ |
| Session / sessions | Account-FK, token_hash eindeutig, csrf_token_hash; recovery-Flag; Ablauf und Widerruf |
| Invitation / invitations | token_hash eindeutig; created_by nullable für Bootstrap ohne Konto; used_by nullable; role, created_at, Ablauf, Verbrauch und Widerruf |
| WebAuthnChallenge / webauthn_challenges | purpose als geprüfter String; challenge binär, payload JSON mit rekursivem JSONValue; optionale Konto-/Einladungs-FKs |
| RecoveryCode / recovery_codes | eine Zeile je Code; (account_id, code_hash) eindeutig |
| FallbackPassword / fallback_passwords | ein Datensatz je Konto; Hash und Algorithmus |
| EmailRecovery / email_recovery | ein Datensatz je Konto; E-Mail, Verifikation, active |
| RecoveryAttempt / recovery_attempts | optionales Konto, kind, optionale code_hash/proof_hash, Ablauf, Verbrauch, nicht negativer Zähler |
| RateLimitEvent / rate_limit_events | Schlüssel und Ereigniszeit, zusammengesetzter Suchindex |

Indizes für Kontozuordnung, Einladungszuordnung, Ablaufbereinigung, E-Mail und Rate-Limits.
Credential-ID nutzt `VARBINARY(1024)` (SQLite akzeptiert denselben Typ mit BLOB-Werten),
weil ein unbeschränktes MySQL-BLOB keine vollständige Unique-Constraint ohne Präfix trägt.
Sonst portable Fluent-Typen; Enums als Strings plus CHECK. Handle-Checks haben einen
kleinen SQL-Dialektzweig (REGEXP/GLOB). MariaDB-Tabellen werden explizit auf
utf8mb4/utf8mb4_bin gesetzt; der vorhandene MySQLNIO-Treiber handelt ebenfalls utf8mb4 aus.
Die DB benötigt CREATE/ALTER/INDEX/DROP-Rechte für Migrationen.

### Atomarer Verbrauch

```swift
try await database.transaction { transaction in
    guard try await SingleUse.consume(.invitation, id: invitationID, on: transaction) else {
        throw RedemptionError.alreadyUsedOrUnavailable
    }
    // Create the account and record used_by on the same transaction database.
}
```

Ressourcen: `.invitation`, `.challenge`, `.recoveryCode`, `.recoveryAttempt`.
Ein bedingtes UPDATE prüft `used_at/consumed_at IS NULL`, gegebenenfalls `expires_at > now`
und bei Einladungen `revoked_at IS NULL`. `ROW_COUNT()` bzw. `changes()` läuft direkt
anschließend auf derselben reservierten Verbindung; genau eine betroffene Zeile gewinnt.
Kein vorgelagertes SELECT als Schutz gegen Rennen. `at:` erlaubt deterministische Tests.
Bei weiteren Schreibvorgängen unbedingt denselben Transaktions-DB-Parameter verwenden;
Fehler zurückwerfen, damit auch der Verbrauch zurückgerollt wird. Innerhalb dieser
Transaktion keine parallelen Tasks auf derselben Verbindung starten.

C2 muss Kontoberechtigung, Proof/Challenge, Versuchslimit, deaktivierte Konten und
Recovery-Sitzungsrechte selbst prüfen; der Helfer ist kein Authentifizierungsdienst.
CSRF speichert nur Hash; Klartext-Token muss C2 erzeugen/ausgeben und bei Bedarf rotieren.
Hash-/Textfelder sind MariaDB-seitig VARCHAR(255); C2 muss passende Längen validieren.

## Prüfstand

Geprüft am 14.10.2026 auf macOS ARM64 mit dem vorhandenen Swift-Toolchain:

```sh
export CLANG_MODULE_CACHE_PATH=/tmp/c1-clang-cache
export SWIFTPM_MODULECACHE_OVERRIDE=/tmp/c1-module-cache
export TMPDIR=/tmp
swift build --disable-sandbox --build-system native
swift test --disable-sandbox --build-system native
```

- Build erfolgreich. Tests: 7 ausgeführt, 1 MariaDB-Test übersprungen, 0 Fehler.
- SQLite in-memory und temporäre Datei: alle Migrationen anwenden, zurücknehmen,
  erneutes Anwenden; Tabellen nach Revert nicht mehr vorhanden.
- Constraints: doppelter Handle, ungültiger Großbuchstaben-Handle, doppelte binäre
  Credential-ID, ungültiger Account-FK, doppelte Session-/Invitation-Tokenhashes,
  doppelte Fallback-/E-Mail-Recovery-Konfiguration werden abgewiesen.
- Binär-/JSON-/Unicode-/UTC-Roundtrips; alle vier Verbrauchsressourcen geprüft.
- Einladungsverbrauch: 24 Tasks, genau ein Gewinner; bei Datei-SQLite vier
  Eventloop-Verbindungen. Verbrauch abgelaufener/widerrufener/fehlender Einladungen
  schlägt fehl. Transaktions-Rollback macht Verbrauch rückgängig.
- XCTVapor: /health 200 auch bei unerreichbarer DB; /ready 503 bei fehlender DB bzw.
  Migrationen, 200 nach Migration, wieder 503 nach Revert. Fehlerform und fehlende
  Weitergabe interner DB-Pfade geprüft.
- CLI mit gebautem `.build/debug/App`: `migrate --revert --yes` (AUTO_MIGRATE=true)
  und `migrate --yes` (AUTO_MIGRATE=false) erfolgreich auf der Smoke-Test-Datei.
  Fluent liefert den CLI; `--revert` nimmt den letzten Batch zurück, `--yes`
  bestätigt die CLI-Rückfrage für Automatisierung.
- `git diff --check`: erfolgreich.

HTTP-Smoke-Versuch:

```sh
DATABASE_DRIVER=sqlite SQLITE_PATH=/tmp/c1-smoke-20261014.sqlite AUTO_MIGRATE=true \
  swift run --disable-sandbox --build-system native --skip-build App serve \
  --hostname 127.0.0.1 --port 18080
curl --include http://127.0.0.1:18080/health
curl --include http://127.0.0.1:18080/ready
```

Migrationen beim Start erfolgreich; der Listener scheiterte an der Sandbox mit
`bind: Operation not permitted`. Beide curl-Aufrufe scheiterten mangels Listener.
Echte HTTP-Prüfung bleibt offen; XCTVapor-Prüfungen sind erfolgreich. Kein Server läuft weiter.
Die temporäre Smoke-Datenbank wurde nach CLI-Prüfung entfernt.

SwiftPM benötigt in dieser Sandbox Cache-Verzeichnisse unter /tmp und den nativen
Build-Modus. Ohne diese Einstellungen scheiterte der globale Modulcache-Zugriff;
der Standard-Xcode-Build scheiterte beim Schreiben temporärer Assemblerdateien.
Verbleibende Warnungen betreffen gesperrte globale SwiftPM-Caches und den als deprecated
markierten nativen Build-Modus, nicht den Anwendungscode. Außerhalb dieser Sandbox
sind normale `swift build`, `swift test` und `swift run App ...` vorgesehen.

### MariaDB-Test aktivieren

`MARIADB_TEST_HOST` aktiviert denselben DB-Test (sonst XCTSkip). Optionale Schlüssel:
`MARIADB_TEST_PORT` (13306), `MARIADB_TEST_USER` (timetrack), `MARIADB_TEST_PASSWORD`
(leer), `MARIADB_TEST_DB` (timetrack_test). Der Test verwendet DB_TLS=off und braucht
eine **leere, dedizierte Testdatenbank**, da er Migrationen und Reverts ausführt.
Befehl: `MARIADB_TEST_HOST=127.0.0.1 swift test --filter DatabaseTests/testMariaDB`
mit den passenden Zugangsdaten und ggf. obigen Sandbox-Buildoptionen.
