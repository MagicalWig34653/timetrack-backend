## Connecting C16 (one adapter file, after both merge)
`registerRoutes` calls `registerMCPRoutes(app, auth: service)`; the authenticator is read per request from `app.mcpAuthenticator` and defaults to rejecting everything (401). Connect with a struct `McpAuthenticator` that calls `authenticateMcpBearer(token, on: db, now: Date())` and maps `McpPrincipal` to `McpAuthPrincipal` (same fields; `credentialKind` `.oauthAccess` -> `.oauthAccess`, `.personal` -> `.personal`; the kind's raw value is stored in `mcp_audit` and the rate-limit key), then assign it in `configure` (replace the TODO in `Routes.swift`). Expect a trivial merge conflict if C16 also touches `DeviceScopeGuard`: both need `/mcp` exempt (and probably `/oauth/*`).

## Decisions beyond the ADR
- JSON-RPC errors: parse/invalid-request/batch use HTTP 400 with the JSON-RPC error body; method-level errors (-32601, -32602) are HTTP 200. Notifications and client responses: 202, empty body. Oversize body: 413 (checked in code; Vapor's collect limit is also set to 256 kb).
- Unknown tool name: JSON-RPC -32602. Missing scope, invalid arguments, and service errors are tool results with `isError: true` and `structuredContent.error.code`. HTTP 403 insufficient_scope on protocol level is not used (tool level only).
- Origin check runs before authentication; requests without Origin (non-browser clients) pass.
- Rate limit counts every authenticated request per credential (120 / 5 min, key `mcp:<kind>:<credentialId>`, table `rate_limit_events`). Invalid-token floods are not counted per credential (there is none); the authenticator owner should limit by IP.
- Audit only for `tools/call` (also scope/validation failures, ok=false). Write failures of the audit never fail the call.
- `start_timer` / `stop_timer`: a generated `clientEventId` when omitted (documented in the description).
- `list_absence_attachments` repeats the 6-line query of `StorageService.attachments` because that service method requires a session `AuthContext`; same account-scoped rules. Could be refactored to a shared account-based method later.
- `view_shared` without `shareId` lists incoming shares (discovery), with `shareId` it returns exactly the REST `SharedViewDTO` (no `...Hm` fields added; a test compares it with the REST response).
- Tools use the service error codes (`segment_overlap`, `absence_overlap`, `timer_already_running`, ...); the generic `bad_request` becomes `invalid_arguments`.
- `create_absence` does not expose document fields; `status` is limited to planned/requested by the schema.
